Subsystem Details

Deep dive into the seven interconnected subsystems

Subsystem Overview

The ESDT is composed of seven interconnected subsystems, each with specialized functions that work together to provide comprehensive digital twin capabilities. These subsystems handle everything from data ingestion to user-facing visualizations.

I Ingest Subsystem

The Ingest Subsystem will inquire and download newly available data and ingest them into our database and shared disk (e.g., Planetary Computer Data Catalog). Our externally sourced data will come from a large variety of providers listed in the architecture diagram.

As our destination will be Azure Blob storage in the Planetary Computer, we will leverage Azure Functions to schedule data acquisitions from each source. Azure Functions provide a method to schedule simple workflows while only using the necessary computing resources to do so as needed (e.g., "serverless" compute), where the main implementation required is a script which can be written in a variety of programming languages.

We will provide individual scripts for each data source as separate Azure Functions which will form the basis of our Ingest Subsystem. We will place the data in their native formats along with necessary cataloguing information.

R Record Subsystem

The Record Subsystem will store externally sourced (from the Ingest Subsystem) and internally generated data (from What-Then, What-Now, and What-Next Subsystems) in an optimized and accessible format into our database and shared disk. It will have the APIs to read and write data into the shared database.

The input data will primarily be available in two common native formats: Cloud Optimized GeoTIFF and NetCDF. An optimal storage strategy would require an API that can map individual array chunks in these files to their byte ranges and retrieving them concurrently and asynchronously, while also allowing for the capability to perform decompression in parallel.

To achieve optimal storage, we will generate kerchunk references information for our datasets which can generate the necessary side-car information that properly maps byte-ranges to array chunks in a manner that is compatible with the Zarr specification.

M Model Subsystem

The Model Subsystem will house land use change and process-based vegetation ecosystem models and generate computationally efficient approximations ("surrogate models") for more responsive What-Next forecasting scenario exploration.

Models will be invoked in either batch or on-demand mode, with a requirement for on-demand models to be responsive within 30 seconds of invocation. In batch mode, models may take longer to run and will be triggered by events or schedules to generate and store results in the Record Subsystem for later access.

The Model Subsystem will leverage Azure cloud services:

  • Azure Batch jobs for high-performance batch processing
  • Serverless Azure Functions for on-demand models triggered by user requests
  • Azure Databricks platform and Azure Machine Learning services for custom workflows, data processing, analysis, and ML model training and deployment

WN What-Then & What-Now Subsystem

The What-Then & What-Now Subsystem will integrate diverse geospatial data layers including satellite imagery, aerial surveys, field observations, and crowdsourced data to generate up-to-date maps delineating:

  • Forest extent and fragmentation
  • Forest structure and carbon
  • Habitat suitability and connectivity corridors across the region

For swift access and manipulation of substantial datasets, we will capitalize on prominent big data processing libraries, including Dask, Ray, Modin, Vaex, and RAPIDS. Advanced geospatial analytics leveraging tools such as ArcGIS, QGIS, and Google Earth Engine will combine the multi-source data using machine learning techniques.

The outputs will include both statistical summaries of total protected areas, vegetation categories, and carbon storage estimates as well as interactive maps and dashboards visualizing the integrated data layers. Automated workflows will refresh the data integration and mapping on a regular basis as new observations become available.

WX What-Next Subsystem

The What-Next Subsystem will forecast the future state of the Central Africa carbon and biodiversity corridors by running land use change, vegetation demography, and ecological models with updated initial states constrained by new observations.

These dynamic simulations will be initialized using the habitat and vegetation maps from the What-Now digital replica to establish accurate starting conditions. Outputs will consist of projected maps animating changes in crucial carbon sinks and habitat connectivity under the currently most anticipated scenario (business-as-usual greenhouse emissions, unchangeable Protected area network).

Interactive visualization will facilitate comparison of present and forecasted conditions. NASA High End Computing (HEC) resources will enable large-scale, high-resolution modeling (e.g., ED2.2 model simulation at a 100 m resolution across Congo Rainforest). We will calibrate our models for a past time frame (2000-2020) and validate them in the subsequent years against ground monitoring data.

V Visualization Subsystem

The Visualization Subsystem will facilitate the visualization of the digital replica and digital forecast via interactive visualization tools. The data visualization tools will be built as several single page applications using the robust and well-supported ReactJS framework.

It will also use the Common Mapping Client (CMC) framework, which was developed at JPL to enable faster and more maintainable development of GIS visualization tools, as a basis for modular and extensible architecture.

The tools will provide users the ability to query and view the various types of data (e.g., NetCDF, GeoTiff, Shape Files) produced by the project as well as manipulate how that data is presented to them. The interface will allow users to view multiple datasets across a wide range of spatial and temporal resolutions.

We will use GeoServer, an open-source and robust tool for GIS applications, to display each dataset. Using CMC and GeoServer in concert will allow the visualizations to be built using community-supported formats and APIs.

F Front-End Subsystem

The Front-End Subsystem will be a web portal with interactive interfaces to products generated by the What-Now Subsystem and the What-Next Subsystem. This subsystem will use the FastAPI Python server framework to provide API services, using FastAPI's asynchronous request processing capabilities to serve requests quickly while reducing slowdowns incurred by I/O overhead.

The Front-End will synthesize and display data from the APIs of the What-Then, What-Now, What-Next, and Visualization subsystems in the forms of maps, time series, animations, and other visualization types.

Using the Python-based framework for the Front-End will allow for the utilization of many GIS, science data, and image processing libraries that are standard in the scientific community. This will allow for more seamless implementation of:

  • GIS queries (leveraging the Azure Maps API)
  • Visualization post-processing
  • Output in formats most commonly used by users

This Subsystem will be designed to be hosted by Azure Apps to simplify deployment and handle scaling and load-balancing.
